## 0. この文書の読み方

### 0.1 この文書は何か

これは**要求の一覧**であり、実装の報告書ではない。既に満たしている要求も、まだ満たしていない要求も同じ形式で並ぶ。満たしているかどうかは各項目の状態タグが示す。

**この文書に書いてよいのは、満たしたかどうかを第三者が判定できる要求だけである。** 「使いやすくすること」「十分な品質にすること」は要求ではない。誰も合否を決められないからだ。判定基準を書けない項目は、要求ではなく §9 の「所感の記録欄」に置く。

### 0.2 状態タグの定義

以前の版では【部分的】が「一部だけ実装した」「実装したが要求に反している」「まだ計測していない」の3つの意味で使われ、読む人が状態を判断できなかった。以下の5語だけを使う。

| タグ | 意味 | 判定 |
|---|---|---|
| **【実装済み】** | 要求を満たしている。根拠として絶対パス＋行番号、または §0.3 の検証IDを持つ | 根拠を辿れば誰でも再確認できる |
| **【未達】** | 実装は存在するが、要求を満たしていない | 何がどう足りないかを本文に書く |
| **【未実装】** | 実装が存在しない | これから作る |
| **【意図的】** | 要求と異なる状態を、理由があって選んでいる | 理由を本文に書く。次の変更で「バグだ」と判断されて壊されるのを防ぐ |
| **【実機のみ】** | 開発環境では判定できず、実機での確認を要する | §9 の実機検証表に記録先がある |

「現在そうなっている」ことは【実装済み】の根拠にならない。**その状態を保つ機構（テストまたは検査）があって初めて【実装済み】と書く。** 例えば「テストが367件ある」は事実だが、件数を検査する仕組みが無ければ、それは【実装済み】ではない。

### 0.3 検証手段（決定済み）

以前の版は「ヘッドレスブラウザ導入かチェックリスト手順書のいずれを採るかは未決定」と書いたまま、その手段を前提にした検証手順を要求として確定させていた。**手段を決める前に手順を要求にしてはならない。** 以下に確定させる。

| ID | 手段 | コマンド／方法 | 何を判定できるか |
|---|---|---|---|
| **V-1** | 純ロジックの単体テスト | `npm test` | 純関数の入出力。DOM・時計・ネットワークに触れない層のみ |
| **V-2** | 仕様の機械検査 | `npm run verify` | 全JSの構文、ファイル構成、import関係、`store.set` の保護、CSP、バイト数、テスト件数など、ソースを読めば決まること（19項目） |
| **V-3** | 実ブラウザでのDOM計測 | ブラウザのコンソールで `getBoundingClientRect` / `elementFromPoint` / `getComputedStyle` / `scrollWidth` を評価する | 実効タップ領域、要素の重なり、横スクロールの有無、計算後のCSS値 |
| **V-4** | 実機（Android実端末） | §9 の表に記録 | カメラ、バイブレーション、Wake Lock、汗ばんだ手でのタップ、見え方、電池 |

**V-3 について。** レイアウト計測は実行できる。このリポジトリの既知の欠陥のうち、「タイマーが最後の種目の✓ボタンの下端29pxを覆ってタップを奪っていた」件と「トーストが14px重なっていた」件は、いずれも `document.elementFromPoint` で発見した。一方、**スクリーンショットの取得と実際のタップ／タッチの配送はできない。** したがって「押した結果どうなるか」は V-3 では判定できず、DOMイベントを直接発火させて代替するか、V-4 に回す。この区別を曖昧にすると、実行できない手順が要求として居座る。

### 0.4 要求番号の付け方

`R<章>.<節>.<連番>`。番号は再利用しない。要求を削除したら番号は欠番のまま残す（過去の議論が参照できなくなるため）。

## 1. アーキテクチャと決定性

### 1.1 層の定義

`js/` 配下の24モジュールを、**外部への依存の種類**で分ける。以前の版はUI層とロジック層と永続化層の19本しか分類しておらず、**外部通信を行うコードが丸ごと未分類だった。** プライバシー境界（§2.7）は「どのファイルが外部通信を持つか」で定義されているのに、層の定義に外部通信層が存在しなければ、境界を守る規則が書けない。

| 層 | モジュール | 依存してよいもの |
|---|---|---|
| **純ロジック層**（8本） | `workout` `nutrition` `energy` `game` `body` `goals` `micronutrients` `calendarView` | 引数のみ |
| **永続化層**（2本） | `store`（localStorage） `photos`（IndexedDB） | ブラウザの保存API |
| **外部通信層**（2本） | `ocr`（Gemini） `barcode`（Open Food Facts） | fetch |
| **動的読み込み層**（1本） | `charts`（`<script>` 注入） | DOM |
| **環境問い合わせ層**（2本） | `storageInfo` `backupReminder` | `navigator.storage` |
| **UI層**（9本） | `ui` `main` `homeTab` `workoutTab` `mealTab` `photoTab` `recordTab` `settingsTab` `dayView` | 上の全て |

**R1.1.1【実装済み】** 純ロジック層8本に `document` / `window` / `localStorage` / `sessionStorage` / `indexedDB` / `navigator` / `fetch(` / `XMLHttpRequest` が出現しないこと。コメント・文字列リテラルは対象外。
検証: **V-2 の R1.1.1**（`scripts/verify-spec.mjs` がコメントと文字列を除去してから走査する）。

> 以前の版は「出現は0件」と書いたが、実際にはコメント内に3件あった。単純な `grep` はコメントを区別できないため、「コメント除く」を人間の目視に委ねていた。検査スクリプトが除去処理を持つ。

**R1.1.2【実装済み】** 純ロジック層に `Date.now()` / 引数なしの `new Date()` / `Math.random()` が出現しないこと。引数付きの `new Date('2026-08-19')` は決定的なので許可する。
検証: **V-2 の R1.1.2**。

**R1.1.3【実装済み】** 外部通信層（`ocr` `barcode`）を import してよいのは UI層のみとする。純ロジック層・永続化層からは import しない。
検証: **V-2 の R2.7.1**（写真系モジュールの推移的import閉包に外部通信層が現れないことを検査する。これが実質的な強制になる）。

**R1.1.4【実装済み】** 動的読み込み層（`charts.js`）の `script.src` に文字列リテラル以外を代入しないこと。
検証: **V-2 の R1.4.1**。

> このアプリで唯一 `<script>` を動的に注入する箇所。変数化されれば任意のスクリプトを読み込む口になる。CSP の `script-src 'self'` が同一オリジンに限定するが、**CSP を1行消せばその防御は消える。** 代入先がリテラルであること自体を門にして二重に守る。

### 1.2 決定性

**R1.2.1【意図的】** `js/game.js` の `badges` は一度獲得したら取り消さない。データを消して同じ入力を与えても、既に持っている称号は消えない。これは非決定的だが**維持する**。`js/game.js:70` に理由がある。称号は罰ではない。

**R1.2.2【意図的・未文書だったものを明文化】** `js/workout.js:150-162` の `Math.max(0, …)` によるボリュームのクランプを削ってはならない。完了したワークアウトが体重データの破損によってXPを減らすことは、設計上あってはならない。このアプリのモチベーション機能はXP減衰・ペナルティを一切持たない。
**このクランプは「冗長な防御」に見えるため、簡潔化のリファクタで真っ先に削られる危険がある。** §1.2.1 と対になる原則として明文化する。

**R1.2.3【実装済み】** `weeklyVolume(workouts, contextFor)` はフォールバック計算にも context を渡すこと。
`contextFor(workout)` は「そのワークアウト日時点の」`exercises` と `bodyweight` を返す関数。日付ごとに変える必要があるため単一のオブジェクトではなく関数で受ける（`migrateHistoricalVolume` が `bodyweightAsOf` を使うのと同じ理由: **今日の体重で過去のボリュームを塗り替えてはならない**）。省略時は従来どおり context 無しで計算する（後方互換）。
検証: **V-1**（`test/workout.test.js` 3件）。

> 以前は `calcVolume(w.sets ?? [])` と context 無しで呼ばれており、`calcVolume` は context 省略時に全種目を `'external'`（外部重量）として扱う。そのため `volume` がスタンプされていないレコード（古いバックアップ・手編集したJSON・インポート経由）は、**自重種目・アシスト種目のボリュームが丸ごと0**として集計されていた。チンニング10回が0kgとして数えられる、という静かな欠落である。
> `volume` がスタンプ済みなら `contextFor` は呼ばない（過去の値を再計算しない）ことをテストで固定している。

**R1.2.4【実装済み】** ボリューム計算の基準体重は、常に「そのワークアウト日時点の体重」（`bodyweightAsOf`）とすること。
根拠: `js/workoutTab.js` の `updateVolume`（画面表示）と `finishSession`（保存）の両方。
検証: **V-1**（`test/workout.test.js` 2件）。`js/workoutTab.js` は DOM に触れるため直接テストできないので、「同じ入力を `bodyweightAsOf` で計算した値と `migrateHistoricalVolume` の結果が一致すること」を固定し、片方だけ変更されたら落ちるようにしてある。

> 以前は `currentBodyweight`（現在の体重）を使っており、`migrateHistoricalVolume` の `bodyweightAsOf` と基準が食い違っていた。日付ビューから3ヶ月前のチンニングを入力すると、今の体重で計算されてしまう。**画面表示と保存の両方を直す必要がある**（片方だけだと、画面の数字と保存される値が食い違う）。

### 1.3 モジュール間の規約

**R1.3.1【実装済み】** `js/ui.js` のヘルパ（`icon` `esc` `toast` `showTab` 等）を呼ぶモジュールは、必ずそれを import すること。
検証: **V-2 の R1.3.1**。

> この検査は、記号文字をSVGアイコンへ置き換えた際に `js/dayView.js` が `icon()` を import せずに呼び、日付ビューを開いた瞬間に `ReferenceError` で画面が真っ白になったことを受けて追加した。純ロジックのテストもファイル走査も素通りする種類のバグである。

**R1.3.2【実装済み】** `innerHTML` に入る文字列のうち、外部由来になりうるものは必ず `esc()` を通すこと。
検証: **V-2 の R1.3.2**。対象は「外部由来の文字列が入りうるプロパティ名」に限定する: `name` `message` `notes` `note` `desc` `description` `label` `title` `text` `brand` `jan` `unit`。

> **検査の範囲を絞った理由。** 最初は「`${...}` に現れる式で `esc()` を通していないもの」を全て報告する形にしたところ **151件**が出た。その大半は数値・内部定数・自前で組み立てたHTML片で、実際の問題は数件だった。**ほぼ誤検出の検査は「毎回出る赤」になり、やがて誰も読まなくなるか検査ごと外される。検査は、出たら必ず直す粒度でなければ意味がない。**
> 絞った結果8件が出て、うち7件を修正、1件（`macro.notes.map(esc)`）は既に対応済みだったため検査側を直した（`<br>` を意図的にHTMLとして出すため、式全体を `esc()` で包むことはできず `map(esc)` が正しい形になる）。

## 2. データ永続性・移行・プライバシー

### 2.1 保存先

| データ | 保存先 | バックアップに含まれるか |
|---|---|---|
| トレーニング・食事・体組成・バドミントン・設定・目標 | localStorage（`mt.` 接頭辞） | 含まれる |
| 体の進捗写真 | IndexedDB（`mt-photos`） | **含まれない** |

**R2.1.1【実装済み】** 体の写真をバックアップJSONに含めないこと。根拠: `js/store.js` の `exportAll` は `DEFAULTS` のキーのみを出力し、写真は `js/photos.js`（IndexedDB）にしか存在しない。

**R2.1.2【実装済み】** `exportAll` は `settings.geminiKey` を空文字にして出力すること。バックアップファイルは端末外に出る可能性があり、APIキーを載せてはならない。根拠: `js/store.js`。

**R2.1.3【実装済み】** `importAll` で `geminiKey` が空なら、端末に既にある値を維持すること。同じ端末へ復元する際にキーを入れ直さずに済むため。

### 2.2 書き込み失敗の扱い

**R2.2.1【実装済み】** `store.set` は「保存してからキャッシュを更新する」順序であること。逆順だと、保存に失敗しても画面上は成功したように見え、リロードで消える。

**R2.2.2【実装済み】** `store.set` の呼び出しは try ブロック内にあること。
例外として `js/main.js` の `loadSeed()` 内は許可する。呼び出し元 `boot()` が捕捉して起動を続け、移行フラグは失敗時に立てない設計（R2.3.1）なので次回起動で再試行される。
検証: **V-2 の R2.2.2**（波括弧の深さを追って try ブロックの内側かを判定する）。

失敗時の扱いは、その保存が何のためかで変える:

| 箇所 | 失敗したら |
|---|---|
| `js/mealTab.js` の `bumpFoodUse` | **記録を続行する。** 並び順が更新されないだけで、食事の記録という主目的は果たせる |
| 食事の削除・食品マスタへの追加 | トーストで伝えて中断する（画面だけ変わって保存されていない状態を作らない） |
| `js/photoTab.js` の称号付与 | トーストで伝えて中断する。保存できていないのに「称号解放」を祝うと、次回起動で消えている |

> **`bumpFoodUse` が最も影響が大きかった。** `addItems`（食事の追加）より先に呼ばれるため、`store.set` が例外を投げると `addFoodById` 全体が中断し、`addItems` に到達せず、**食事が記録されないままトーストも出なかった。** R4.7.4（1タップで1品追加）と R4.7.5（失敗を成功トーストで上書きしない）を、その直前の1行が無効化していた。

### 2.3 移行

**R2.3.1【実装済み】** 移行フラグ（`exercisesSyncedV2` `foodsMacroSyncedV1` `foodsMicroSyncedV1` `volumeModelMigrated`）は、移行が成功したときだけ立てること。失敗時に立てると、一度失敗したデータは永久に移行されない。

**R2.3.2【実装済み】** 種データの取得（`data/*.json` の fetch）が失敗しても起動を止めないこと。`res.ok` を確認し、`.json()` の失敗を隔離した try/catch で捕まえ、`initTabs()` は必ず実行する。根拠: `js/main.js` の `boot()`。

**R2.3.3【実装済み】** 種データの取得は `initTabs()` より**後**に待つこと。
検証: **V-2 の R6.5.1**。詳細は §6.5 を参照。

### 2.4 永続化の要求

**R2.4.1【実装済み】** 起動時に `navigator.storage.persist()` を呼ぶこと。Androidは空き容量不足時にサイトデータを削除する対象を選ぶが、永続化を許可されたオリジンは対象から外れる。体の写真をIndexedDBに持つこのアプリは、呼ばなければ消える側に入る。根拠: `js/main.js` の `boot()` 冒頭、`js/storageInfo.js`。

**R2.4.2【実装済み】** 設定タブに、永続化の状態・使用量・各データの件数を表示すること。「消えたかどうか」を利用者が自分で確認できなければ、消えたことに気づけない。根拠: `js/settingsTab.js` の「データの状態」カード。

**R2.4.3【実装済み】** 一定期間バックアップしていなければ促すこと。根拠: `js/backupReminder.js`。

### 2.5 安全設定の値域（全経路で強制）

**R2.5.1【実装済み】** `profile.targets` の値域は、**値がストアに入る全ての経路**で検証すること。設定画面の保存ボタンだけでは足りない。

以前は設定タブの `kcalFloor >= 1200` ハードブロックだけが存在し、バックアップJSONを手で編集して `{"profile":{"targets":{"kcalFloor":1}}}` をインポートすれば、そのブロックを完全に迂回して安全装置を無効化できた。

検証する値域:

| 項目 | 条件 |
|---|---|
| `protein` `kcalMin` `kcalMax` `kcalFloor` | 有限の数値かつ 0 より大きい |
| `alcoholMl` | 有限の数値かつ 0 以上 |
| `kcalFloor` | `MIN_KCAL_FLOOR`（1200）以上 |
| `kcalMin` | `kcalMax` 以下 |
| `kcalMin` `kcalMax` | いずれも `kcalFloor` 以上 |
| `dayOverHour` | 0〜23の整数 |

根拠: `js/store.js` の `isValidSafetyTargets`（インポート経路）、`js/settingsTab.js` の保存ハンドラ（画面経路）。
検証: **V-1**（`test/store.test.js` の「importAll は…を弾く」6件）。変異テストで確認済み（§5.2）。

> **`kcalMax >= kcalFloor` を課す理由。** 上限が警告ラインより低い設定は「目標どおりに食べると必ず警告ラインを割る」自己矛盾した状態である。加えて、後述 R3.2.1 の欠陥があった間は、`kcalMax` を下げるだけで「食べなさすぎ」警告そのものを到達不能にできた。判定側は修正したが、入力側でも同じ穴を塞ぐ。**安全装置を1箇所の修正に依存させない。**

### 2.6 レコード形式の検証

**R2.6.1【実装済み】** `importAll` は全キーを検証してから書き込むこと。1つでも不正なら何も書き込まない。書き込み途中で失敗したら、書き込み済みの分を元に戻す。

**R2.6.2【実装済み】** レコード形状の検証を `meals` `workouts` `body` `badminton` `foods` の5キーに適用すること。
検証する内容は「集計側がそのレコードを数えるために最低限必要なフィールド」だけに絞る。過剰に厳しくすると、古いバージョンで作った正当なバックアップが復元できなくなる。

| キー | 必須 | 理由 |
|---|---|---|
| `meals` | `datetime`(文字列) / `items`(配列) | 無ければ `dayTotals` に数えられない |
| `workouts` | `date`(YYYY-MM-DD) / `sets`(配列) | 無ければ `weeklyVolume` にも `programStatus` にも数えられない |
| `body` | `date` / `weight`(数値) | `muscle` `fatPct` は体重計だけの記録もありうるので必須にしない |
| `badminton` | `date` / `durationMin`(数値) | 無ければ運動消費に数えられない |
| `foods` | `id`(文字列) / `name`(文字列) | 無ければクイック記録にも食事の追加にも使えない |

検証: **V-1**（`test/store.test.js` 5件）。

> 形だけ配列であれば中身が何でも通る状態だった。日付を欠いたワークアウトは集計側が防御的に読み飛ばすため例外は出ないが、**利用者から見れば記録が消えている。** 黙って受け入れるより、インポートを断ってバックアップを選び直してもらう方がよい。

### 2.7 プライバシー境界

#### 2.7.1 何が出て、何が出ないか

**外部に出るもの**（利用者が明示的に操作したときだけ）:

| 送信先 | 内容 | 経路 |
|---|---|---|
| Google（Gemini API） | 食事写真、レシート画像、**InBody結果紙の画像** | `js/ocr.js` |

**外部に出ないもの**: 体の進捗写真、保存済みの体重・体組成の履歴データ、トレーニング記録、食事ログ、目標設定。

**R2.7.0【意図的】InBody結果紙の画像は「体組成の数値」を含むが、送信を許容する。**
以前の版はここを「絶対に出てはならないもの: 体重・体組成」と「出てよいもの: InBody結果紙の画像」に分けて書いており、同じ節の中で矛盾していた。判断を確定させる:

- **保存済みの履歴データ**は、いかなる操作でも送信しない。1回の操作で送るものと、蓄積した記録全体を送ることは別物である。

根拠: `js/ui.js` の `confirmSend(file, kindLabel)`。InBody結果紙（`js/homeTab.js`）・食事写真・レシート（`js/mealTab.js`）の3経路すべてが通る。表示用の ObjectURL はどの分岐で閉じても `revoke` する。
検証: 実ブラウザでダイアログの表示・画像の読み込み・キャンセル時の戻り値 false・ObjectURL の解放を確認済み。

> `capture="environment"` はヒントに過ぎず、Androidではギャラリー選択に切り替えられる。**利用者が誤って体の進捗写真を選ぶ経路が実在する。** 以前の確認ダイアログは解析「結果の数値」しか見せておらず、その時点で送信は既に終わっていた。

#### 2.7.2 境界の強制方法

**R2.7.2【実装済み】** 体の写真を扱うモジュール（`js/photos.js` `js/photoTab.js`）から**静的importで到達できる範囲**に、外部通信コードが存在しないこと。

> **なぜファイル単位の grep では不十分か。** 以前の版は「`js/photos.js` と `js/photoTab.js` に対する `fetch(|XMLHttpRequest|…` の grep が0件」を合否条件にしていた。しかし**同じ grep は `js/homeTab.js` に対しても0件を返す**。にもかかわらず `homeTab.js` は `import { analyzeInbody } from './ocr.js'` 経由でGoogleに画像を送っている。つまりこの grep は送信経路の不在を証明しない。`js/photoTab.js` に import を1行足せば、grep は依然0件のまま体の写真が送信可能になる。**推移的な到達可能性で検査しなければ、守られるものは何もない。**

検証: **V-2 の R2.7.2 と R2.7.3**（CSPの存在と内容、およびコード内の外部ホストがCSPの許可先と一致すること）。

> **CSP が最も重要な理由。** R2.7.2 の import 検査は「今の実装がそうなっている」ことを保証するが、CSP は「どのファイルがどう import しようと、ここに書かれていない宛先へは送れない」ことをブラウザに強制させる。前者は約束、後者は機構である。以前の版は §6.3「外部リクエスト禁止」という章を丸ごと割きながら、その章の合否条件が「規約として明記する」＝人間の約束だった。

## 3. 科学的根拠と安全装置

### 3.1 このアプリが守るもの

利用者は過去に、週5日のトレーニングを続けながら1日1,200kcal、次いで1,000kcalへの減量を提案した経緯がある。**このアプリの安全装置は、上限（食べすぎ）ではなく下限（食べなさすぎ）を守るために存在する。** 上限側の警告は常に `info` 止まりで、下限側だけが `danger` を出す。この非対称性は仕様であり、対称に「整える」リファクタをしてはならない。

### 3.2 カロリー判定の構造

**R3.2.1【実装済み】** 下限（EAフロア）の判定は、上限超過の判定と**独立に**評価すること。排他分岐にしてはならない。

以前の実装は次の形だった:

```js
if (kcal > targets.kcalMax) { kcalOver(info) }
else if (dayOver) { if (kcal < floor) { kcalFloor(danger) } }
else { kcalRemaining(info) }
```

`kcal > kcalMax` が成立した瞬間、**下限判定に到達しない。** 設定タブは `kcalMax` に下限規制を持っていなかったため、`kcalMin=1000, kcalMax=1000, kcalFloor=1440` は全ての検証を通過して保存できた。この設定で1,100kcal摂取した日（EAフロアは約1,624kcal）に表示されるのは:

- `1100 > 1000` → **「目標を100kcal超えています」（info）**
- 下限判定には到達しない → **danger は出ない**

**「食べなさすぎ」の状態で「食べすぎ」と表示されていた。** 1,200→1,000kcal を2度提案した利用者に対して、設計意図の完全な反転である。`kcalFloor >= 1200` のハードブロックは、塞ぐべき穴の隣を塞いでいた。

現在の実装（`js/nutrition.js` の `achievement`）:

```js
const belowFloor = kcal > 0 && Number.isFinite(floor) && floor > 0 && kcal < floor;
if (dayOver && belowFloor)            → kcalFloor(danger)
if (!belowFloor && kcal > kcalMax)    → kcalOver(info)
else if (!dayOver)                    → kcalRemaining(info)
```

検証: **V-1**（`test/nutrition.test.js` の「kcalMaxを下限より低く設定しても、下限割れのdanger警告は出る」他3件）。変異テストで確認済み（§5.2）。

**R3.2.2【実装済み】** フロアを下回っている間は上限超過（`kcalOver`）を出さないこと。EAフロア未満の状態で「目標を超えています」と伝えるのは、摂取を減らす方向へ誘導することになり、このアプリの目的と正面から反する。

**R3.2.3【実装済み】** 「残り◯kcal」と達成率バーのアンカーは、`kcalMin` と EAフロアの**大きい方**とすること。`kcalMin` は利用者が自由に下げられる値なので、それだけを基準にすると `kcalMin=1000` の利用者は900kcal時点で「残り100kcal」＝もうすぐ終わり、と読み、1,000kcal食べた時点でバーが緑（達成）になる。実際のEAフロアは約1,624kcalである。

**R3.2.4【実装済み】** ceiling系の警告レベルは `info` を超えないこと。
合否条件: `js/nutrition.js` の `achievement()` が返す警告のうち、`type` が `kcalOver` であるものは必ず `level === 'info'` であること。
検証: **V-1**（`test/nutrition.test.js`）。

### 3.3 時刻ポリシー

**R3.3.1【実装済み】** 「その日の食事はほぼ終わった」とみなす時刻は `profile.dayOverHour`（既定22時、0〜23の整数）とし、利用者が設定タブから変更できること。

以前は `new Date().getHours() >= 20` の固定値だった。**この利用者の食生活は「朝にプロテイン＋夕食1食」で、夕食の時間帯は19〜21時である。** 20時の時点で摂取は朝のプロテインのみ（数百kcal）で、夕食はこれから食べる。つまり `kcal > 0 && kcal < floor` が成立し、**毎日、夕食の直前に「◯◯kcal は少なすぎます」という danger 警告が出ていた。** 毎日必ず誤爆する警告は数日で無視されるようになり、本当に足りていない日の警告まで一緒に殺す。

この閾値は「まだ食べる予定があるか」の代理変数であり、食事回数が少ない人ほど遅い時刻に置く必要がある。固定値にしてはならない。

**R3.3.2【実装済み】** `isDayOver` は閾値の型と整数性を先に確かめること。`Number()` を通してから範囲を見てはならない。`Number(null)` `Number('')` `Number([])` はいずれも `0` になり、「0時」という妥当な閾値として通る。設定が壊れた端末で **常に `dayOver === true`＝一日中 danger 警告** という最悪の誤爆に化ける。
検証: **V-1**（`test/nutrition.test.js` の「閾値が不正なら既定値へフォールバックする」）。

> この欠陥は、私が書いた最初の実装に実際に存在し、追加したテストが発見した。

**R3.3.3【実装済み】** 2つの安全装置が異なる時刻ポリシーを持ってはならない。`js/recordTab.js` の `checkRateSignals` に渡すエネルギー可用性も、`achievement()` と同じ `dayOver` で判定すること。

以前は `checkRateSignals` にゲートが無く、朝プロテイン150kcalだけの状態で記録タブを開くと EA ≈ 2 kcal/kgFFM/日 となり、**「緊急域（25未満）」が表示されていた。** 同一コードベース内で、片方は日中の誤爆を防ぎ、もう片方はそれを無視していた。

**R3.3.4【実装済み】** EAが緊急域（`EA_EMERGENCY_PER_KG_FFM` = 25 kcal/kg FFM/日 未満）と判定されたら、ホームタブの初期表示に出すこと。
根拠: `js/homeTab.js` の `renderSafetyCard`。判定には `achievement()` と同じ `dayOver` ゲートを通す（R3.3.3）。
検証: 実ブラウザで摂取500kcal・FFM48kgの状態を作り、ホームに「今日のエネルギー可用性は 10.4 kcal/kg FFM/日 で、緊急域(25未満)です」が出ることを確認済み（検算一致）。

> 以前 `checkRateSignals` の唯一の呼び出し元は記録タブの目標カードだった。このアプリで最も強い警告が、月に数回しか開かないタブの下の方にしかない状態は、警告として機能していない。
> 閾値 25 / 30 は `js/goals.js` の `EA_EMERGENCY_PER_KG_FFM` / `EA_WARNING_PER_KG_FFM` に切り出した。以前は `checkRateSignals` の中にリテラルで埋め込まれており、ホームから同じ基準で判定しようとすると数値を二重に持つことになった。**閾値が2箇所にあると、片方だけ変更されて画面ごとに違う判定が出る。**

**安全カードは、条件を満たしたときだけ描画すること。** 常設すると壁紙化し、本当に出たときに読まれなくなる。また警告だけでなく次の行動への導線（「食事を記録する」ボタン）を伴うこと。

### 3.4 ステータスバーの再計算

**R3.4.1【実装済み】** ステータスバーは、以下のいずれかが起きたら描き直すこと。

| 契機 | 実装 |
|---|---|
| アプリが前面に戻ったとき | `js/mealTab.js` の `visibilitychange` |
| 食事の追加・削除 | `js/mealTab.js` |
| 目標の保存 | `js/settingsTab.js` |
| トレーニングの保存 | `js/workoutTab.js` の `finishSession` |

以前は起動時・食事の追加・食事の削除の3経路しか無く、**安全警告の唯一の常設表示面が食事の追加削除でしか更新されなかった。** 帰結は4つ:

1. `dayOver` が起動時の値のまま凍る。18時に開いたまま（トレーニング中はWake Lockで画面が点いたまま）22時になっても警告は出ない。
2. 日付も起動時に固定される。standalone PWA はAndroidで再開されることが多く、日付を跨ぐと前日の合計が今日のバーに出続ける。
3. 設定で目標を変えてもバーは古い目標のまま。
4. トレーニングを保存して運動消費が増えても、EAフロア（30 × FFM + 運動消費）が上がらない。運動した日ほど緩いフロアのまま表示される。

**この4件と R3.3.1（誤爆）は相互作用する。** 再描画だけを足して閾値を20時のまま残せば、1と2は直るが誤爆は悪化する。閾値だけを直して再描画を足さなければ、22時になっても警告は出ない。**両方同時に直す必要がある。** この相互作用が文書化されていなかったため、片方だけ直して悪化させる事故が起きうる状態だった。

**R3.5.4【実装済み】** `js/energy.js` `js/goals.js` `js/micronutrients.js` の数値定数に、出典または区分ラベルがあること。
検証: **V-2 の R3.5.4**。認めるのは (a) 著者・年・機関名、(b)「出典なし」「実務上の仮定」、(c)「設計上の判断」「製品仕様」のいずれか。**黙って数字だけを置くことを禁じる。**

> **「直前20行」ではなく「その定数に付いているコメント」を見る。** 最初は直前20行を窓にしたが、これらのファイルは冒頭に長い出典コメントを持つため、**出典の無い定数をその近くに置くだけで検査を通ってしまった**（実際に `MAGIC_THRESHOLD = 42` を足しても合格した）。現在は直前の連続したコメント塊のみを根拠として認める。連続した定数宣言は1つのコメントを共有するのが普通なので、同じ形の宣言だけは読み飛ばして遡る。

### 3.6 「不明」と「0」の区別

**R3.6.1【実装済み・未文書だったものを明文化】** `js/nutrition.js` の `dayTotals` は、脂質・炭水化物・食物繊維・ビタミンD・カルシウム・食塩の6項目について `*Known` フラグを返す。その日1件でも欠損があれば `false` になる。

**これは安全装置である。** 未記録の栄養素を「0」として表示すると、「足りている」という誤った安心材料を与えかねない。「未記録なのに0と表示する」方が実装は単純なので、簡潔化の対象になりやすい。**削ってはならない。**

**R3.6.2【実装済み】** 運動消費が計算できないとき、EAフロアを固定値へ緩めてはならない。判定そのものを保留すること。

`dailyExerciseKcal` は体重が不正・未指定なら `null` を返す。`eaFloorKcal` / `energyAvailability` / `equationMaintenanceEstimate` はいずれも `exerciseKcal === null` を「不明」として `null` を返す。`achievement()` は下限判定を行わず `{ type: 'eaUnavailable', level: 'warn' }` を1件返す。
検証: **V-1**（`test/energy.test.js` 4件、`test/nutrition.test.js` 3件）。

> 以前は 0 を返し、コメントには「運動消費不明で計算を止めるより、EA計算側で『運動0』として安全側に振れる方を優先する」と書かれていた。**向きが逆である。** EAフロアは 30 × FFM + 運動消費kcal なので、0 として扱えばフロアは運動分だけ下がる。週5日運動している人に「運動していない人の下限」を適用することになる。**分からないことを理由に基準を緩めれば、それは安全装置ではない。**
> 旧仕様を固定していたテスト（「weightKgが不正なら0」）も、誤った挙動を守っていたものとして更新した。
> `undefined`（未指定）は従来どおり 0 として扱う（後方互換）。「不明」を意味するのは明示的な `null` だけである。

### 3.7 記録の欠落

**R3.7.1【実装済み】** 食事記録が `MEAL_LOG_GAP_DAYS`（3日）を超えて途切れたら、ホームタブに表示すること。
根拠: `js/nutrition.js` の `daysSinceLastMealLog` と `MEAL_LOG_GAP_DAYS`、`js/homeTab.js` の `renderSafetyCard`。
検証: **V-1**（`test/nutrition.test.js` 4件）。実ブラウザで5日途切れた状態を作り、ホームに「食事の記録が5日途切れています」が出ることを確認済み。

> `achievement()` は `kcal === 0`（まだ何も記録していない日）を danger の対象にしない。1日の途中で「0kcalです」と言われても意味が無いためで、その判断自体は正しい。しかし帰結として、**食事を記録しなくなれば EA関連の警告はすべて消える。** 「食べていないから記録しない」と「記録していないから警告が出ない」が区別できない。極端な減量志向の再発は、まさに記録が途切れる形で現れる。**沈黙を「問題なし」と解釈しない。**
> 3日という値は、週3回のトレーニング周期（A/B/C）を1周する長さ。これを超えると「たまたま忘れた」ではなく習慣が止まっている可能性が高い。

### 3.8 アルコール

**R3.8.1【意図的】** `targets.alcoholMl` の既定値 500ml は、利用者の習慣値と同じである。判定は `alcoholMl > targets.alcoholMl` なので `500 > 500` は false となり、**習慣どおり飲んでいる限り「超過」状態にはならない。**

これは欠陥ではない。500ml・5% の純アルコールは 20g であり、MHLW「飲酒ガイドライン」(2024) の「節度ある適度な飲酒」の上限そのものである。ガイドライン上の適量を「超過」と表示するのは誤りになる。バーは 0〜500ml の範囲で摂取量を示す用途で機能している。

ただし**この帰結が文書化されていなかった**ため、「バーが一度も点灯しない＝壊れている」と判断されて閾値を下げられる危険があった。明文化する。

**R3.8.2【意図的】アルコール由来のkcalはEAの分子に算入する。**

理由: EA（エネルギー可用性）は「総摂取エネルギー」で定義されている（Mountjoy et al. ACSM/AND/DC 2016）。除外すると、文献の 30 / 45 kcal/kgFFM/日 という基準値と比較できない独自の数字になり、**閾値の根拠そのものが失われる。**

ただしアルコール由来のエネルギーが筋タンパク質の合成に使われないことは事実なので、記録タブのEAカードで内訳（何kcal・全体の何%）を明示する。根拠: `js/recordTab.js` の `renderEnergyCard`。

**警告としては出さない。** 毎日500ml飲む習慣に対して割合で警告を出せば毎日必ず点灯し、R3.3.1 で直した `dayOver` の誤爆と同じ「無視される警告」になる。

> 以前は `js/micronutrients.js` のコメントが同じ220kcalを「1日のカロリー予算のうち最も手軽に取り戻せる」余剰と位置づけ、一方 `js/nutrition.js` はそれを安全下限を満たすエネルギーとして数えていた。**同一コードベースが2つの立場を同時に取っており、どちらで実装すべきか誰も決められない状態だった。** 「削れる余剰」という表現は削除した。

## 4. UI・操作性・モバイル

前提: 利用者はジムでこのアプリを開く。**手は汗ばんでいる。立っている。セット間の休憩は90秒。** これらは「配慮すべき点」ではなく、要求の前提条件である。

### 4.1 タップ領域

**R4.1.1【実装済み】** アプリ自身が描画する操作可能要素の実効タップ領域は、下表の基準を満たすこと。

| 対象 | 基準 | 出典 |
|---|---|---|
| 通常のボタン | 48×48 CSS px | Material Design の推奨最小タッチターゲット(48dp) |
| ✓セットボタン | 56×56 CSS px | 上記より一段大きく。最も連打され、汗ばんだ手で押される唯一のコントロール |
| カレンダーの日セル | 44×44 CSS px | WCAG 2.1 SC 2.5.5 Target Size (Enhanced, Level AAA) |

参考: WCAG 2.2 SC 2.5.8 Target Size (Minimum, Level AA) は 24×24 CSS px。本アプリはこれを大きく上回る基準を自ら課している。根拠は `css/style.css` の `button` ルール上のコメントに記載。

実測（V-3、375×812）: `.setbtn` 18個すべて 56×56 で `elementFromPoint` の中心が自分自身。`.cal-cell` は 45.1×48.0。

> **日セルだけ44を採る理由。** 375px幅で7列＋週次回数列を並べると、1セルは最大でも45px前後にしかならない。48pxまで広げるには回数列を捨てるか横スクロールを許すしかなく、どちらも失うものの方が大きい。日セルは「記録するボタン」ではなく詳細画面への遷移であり、誤タップの代償が小さい。
> カード左右のパディング(12px)へ `margin: 0 -8px` ではみ出させて 42.7px → 45.1px を確保した。

**R4.1.4【実装済み】** `prompt()` を使わないこと。入力はアプリ自身が描画するフォームで行う。
検証: **V-2 の R4.1.4**。

> ブラウザ標準ダイアログはボタン寸法をアプリが制御できず、R4.1.1 の対象外に落ちる。そのうち `prompt()` は文字・数値の入力を伴うため、汗ばんだ手で立ったまま操作するという前提と最も強く衝突する。
> 除去した3経路:
> - `js/dayView.js` — 1品追加するのに `prompt()` を**3連続**で出していた。`js/mealTab.js` の `openItemForm`（自前フォーム）を使い回すよう変更。R4.7.4「1タップで1品追加できる」とも矛盾していた。
> - `js/homeTab.js` — バドミントンの分数入力。実質毎回60を確定するだけの操作なので、30/60/90/120分の選択式にした（1タップで完了）。
> - `js/barcode.js` — 品名が取れなかったときの入力。**通信層が画面を出していた。** 「名前が無い」という事実だけを返し、どう尋ねるかは UI層が決めるよう変更。

**R4.1.5【意図的】** `confirm()` は取り消せない操作の確認に限って使ってよい。
選択肢が2つでボタンも大きく、誤操作の危険はむしろアプリ自作のダイアログより低い。使用箇所: 記録の削除、プログラム切り替えによるセット破棄、同日重複の確認、バックアップの上書き。

**R4.1.2【実装済み】** ✓セットボタンは 56×56 px 以上、外余白 4px 以上とすること。このアプリで最も連打されるコントロールであり、汗ばんだ手で最も外しやすい。根拠: `css/style.css`。

**R4.1.3【実装済み】** 固定配置の要素（タイマー・トースト）が、他の操作可能要素のタップを奪わないこと。
根拠: タイマーは `pointer-events: none` と `body.timer-active` によるパディング、トーストも同様の処理。
発見の経緯: タイマーは最後の種目の✓ボタンの下側56pxのうち29pxを、トーストは14pxを覆っていた。いずれも **V-3 の `document.elementFromPoint`** で発見した。
検証: **V-3**（タイマー表示中・トースト表示中・最下部スクロール状態で、全 `.setbtn` の中心と四隅の5点について `elementFromPoint` が当該ボタン自身を返すこと）。

**R4.7.2【実装済み】** 休憩タイマーは90秒。根拠: `js/workoutTab.js` の `REST_SECONDS`。

**R4.7.3【実装済み】** トレーニング中は Screen Wake Lock で画面を保持すること（設定でOFFにできる）。セット間90秒のたびに画面が消え、汗ばんだ手でロック解除する手間を無くすため。ページが隠れるとブラウザ側で強制解放されるため、再表示時に再取得すること。根拠: `js/workoutTab.js`。

※ ただし R2.2.2 の未保護な `store.set` により、この保証は現在部分的に破れている。

**R4.7.5【実装済み】** 保存に失敗したときに、成功トーストで上書きしないこと。

**R4.7.6【実装済み】** キャッシュ済み・回線正常の状態で、ページ読み込み開始から `.setbtn` がタップ可能になるまで **2秒以内**であること。
実測（V-3、2026-08-19）: `loadEvent` 35ms + トレーニングタブ切替から `.setbtn` 到達まで 2ms = **37ms**。

> **90秒という休憩時間が意味するのは時間予算である。** タップ数だけを比較しても、起動が数十秒かかれば意味が無い。
>
> この予算を守るために `sw.js` の `NETWORK_TIMEOUT_MS` を 2500ms から **800ms** に下げた。ここで待つのは「手元に使えるキャッシュがあるのに、もっと新しいものが来ないか確かめている」時間であり、回線が正常なら同一オリジンの小さなアセットは数十msで返る。返らないなら待つ価値のある遅延ではない。2500ms のままでは、回線1本で予算の大半を使い切ってしまう。
> タイムアウトしてもネットワーク側の Promise は中断しないため、遅れて到着した応答はそのままキャッシュを更新する（次回起動では新しいバイト列が使われる）。

### 6.1 初回ロード予算

**R6.1.1【実装済み】** 初回訪問で発生する**全ネットワーク転送**が 640 KiB（655,360 B）以内であること。
「全ネットワーク転送」には Service Worker の install 時に `cache.addAll(ASSETS)` が取得する分を**含む**。
現在値: **579,904 B（566.3 KiB）／ ASSETS 32件**

| 内訳 | バイト |
|---|---|
| `js/` | 332,759 |
| `vendor/`（Chart.js） | 208,532 |
| `css/` | 15,324 |
| ルート（`index.html` `manifest.json` `sw.js`） | 11,800 |
| `data/` | 7,364 |
| `icons/` | 4,125 |

検証: **V-2 の R6.2.1**。

> **なぜ定義を変えたか。** 以前の版は「ページ読み込み時に読まれるファイル」だけを数えて 351,348 B とし、「予算400 KiBに対して余裕58,252 B」と評価していた。しかし `sw.js` の install ハンドラは `cache.addAll(ASSETS)` を無条件に実行し、ASSETS には `vendor/chart.umd.js`（208,532 B）が含まれる。**初回訪問時、ブラウザは実際には約560KBをダウンロードしていた。** 予算という数値要求で最も重要なのは「何を数えるか」であり、そこが誤っていた。誤った値を自動計測しても意味が無い。
>
> **Chart.js を ASSETS に残す理由。** 外せば初回転送は352KBになるが、記録タブを一度もオンラインで開いていない状態でグラフが出なくなる。このアプリはオフライン動作が要件で、ジムのWi-Fiは不安定である。208KBの一度きりのコストと引き換えに、オフラインでの確実性を取る。
>
> **640 KiB という値の根拠。** 現在値 566.3 KiB に対し、Chart.js 相当（約200KB）をもう1つ追加できない程度の余裕（約74KB）を残した値。「今の実装が偶然収まる値」ではなく「大きな依存をもう1つ増やそうとしたら落ちる値」として設定している。

**R6.1.2【実装済み】** Chart.js を index.html から静的に読み込まないこと。`<script src>` は `js/main.js` の1本だけであること。
根拠: `js/charts.js` の `loadChartJs()` が動的に注入し、同一のPromiseを再利用する。`js/recordTab.js` が記録タブを開いたときだけ呼ぶ。
検証: **V-2 の R6.2.2**。
※ これで削減できるのは**クリティカルパスでの解析・実行**であり、ダウンロードではない（R6.1.1 参照）。ホーム画面を開くだけのときに Chart.js のパースと実行が走らない、という効果は実測で確認している。

### 6.2 オフラインと不安定な回線

**R6.2.1【実装済み】** Service Worker の取得戦略を2つに分けること。

| 対象 | 戦略 | 半死の回線での待ち時間 |
|---|---|---|
| ナビゲーション（`index.html`） | ネットワーク優先＋800msのタイムアウト | 最大800ms |
| サブリソース（`js` / `css` / `data` / `vendor`） | キャッシュ即返し＋背景で更新（stale-while-revalidate） | **0ms** |

検証: **V-2 の R6.4.2**（タイムアウトの存在と上限、`staleWhileRevalidate` の存在、ナビゲーションだけが `networkFirst` へ分岐すること）。

> **なぜ分けたか — 計測で分かったこと。**
> 全てをネットワーク優先（タイムアウト800ms）にしていたとき、応答の返らない回線での起動を実測したら **8.08秒**かかった。HTML自体は812msでキャッシュから返っていたにもかかわらず、である。
>
> 原因はESモジュールの読み込みが依存関係の段数だけ待たされること。`index.html` → `js/main.js` → その import → さらにその import…と辿るため、**1本あたり800msのタイムアウトが段数分積み上がる。** 24本のモジュールが並列に取得されるわけではない。タイムアウトを短くしても段数は変わらないので、この方向には限界がある。
>
> サブリソースを stale-while-revalidate に変えた結果、同じ条件で **825ms**（`responseEnd` 807ms ＝ ナビゲーション1本ぶんのタイムアウト）になった。**8083ms → 825ms。**
>
> **失うもの:** デプロイの反映が「次回の起動」に一段遅れる。背景の再取得でキャッシュは更新されるので、2回目の起動では新しいバイト列が使われる。ジムで開いたアプリが8秒間何も表示しないことの方がはるかに悪い。

**R6.2.2【実装済み】** キャッシュが無い場合（初回訪問・新規追加ファイル）はタイムアウトを付けないこと。
返せるものが無い以上、待つ以外の選択肢が無い。ここで打ち切るとアプリそのものが起動できなくなる。

**R6.2.3【実装済み】** 取得に失敗した同一オリジンのサブリソース（`js/` 画像等）に対して `index.html` を200で返さないこと。本当のエラーが隠れる。ナビゲーション（ページ遷移）だけはアプリシェルへフォールバックしてよい。

**R6.2.4【実装済み】** `sw.js` の `ASSETS` が、実行時に必要なファイルを過不足なく含むこと。
検証: **V-2 の R6.4.1**（ASSETS 32件が `js/` 24本＋`css/`＋`data/`＋`vendor/`＋`index.html`＋`manifest.json` を網羅していること）。

**R6.2.5【実装済み】** オフライン時に、全6タブが描画され、セットの記録が保存できること。
**実測（V-3、2026-08-19）**: 開発サーバーを実際に停止した状態で検証。

理由は、このアプリの UI 要求がどれもレイアウト計算を必要とするから。実効タップ領域（R4.1.1）、要素の重なり（R4.1.3）、横スクロールの有無（R4.2.1）は、いずれも `getBoundingClientRect` / `elementFromPoint` の**実際の値**でしか判定できない。jsdom はレイアウトを計算せず全要素が 0×0 を返すため、**このアプリが UI に対して立てている要求を1つも判定できない。** 判定できない環境を入れれば「テストがある」という見かけだけが増える。

代わりに UI層は次の2つで担保する:
- **V-2（機械検査）** — 構文、import の整合、`store.set` の保護、`esc()` の適用、記号文字、スプライト参照
- **V-3（実ブラウザでのDOM計測）** — タップ領域、重なり、横スクロール、起動時間

**ただし「DOMに触れないのにテストが無い」モジュールは埋めること。** 今回 `js/ocr.js` の `parseItems` / `parseBody`（Geminiの応答を解釈する純関数＝外部から来た信頼できない文字列を最初に受け取る場所）と `js/ui.js` の `esc()`（XSS防御の中核）にテストを追加した。

## 7. ベンチマーク — 「AAA品質」の定義

### 7.1 何と比べるか

「世界的に評価が高い」は評価ではなく評判である。**比較対象を名指しし、軸ごとに測る。**

| 軸 | 基準とするアプリ | なぜこのアプリか |
|---|---|---|
| トレーニング記録の速さ | Strong / Hevy | セット記録の手数がこのカテゴリで最も少ない部類 |
| 部位別の負荷の可視化 | Fitbod | 「どこを鍛え、どこが空いているか」の提示に特化している |
| 食事記録の手数 | MyFitnessPal / あすけん | あすけんは日本人の食事摂取基準に準拠しており、この利用者の基準値と直接比較できる |
| 体組成の扱い | InBody公式アプリ / Withings | 測定誤差とトレンドの区別を扱っている |
| 継続の仕掛け | Whoop / Oura | 「今日どうするか」を1画面で示す設計 |

**このアプリは上記のどれとも目的が違う。** 独自性（EAフロアによる下限保護、体の写真を端末外に出さない、日本の食事摂取基準への準拠）を捨てて似せるのではなく、**下の6軸それぞれで測定値が基準アプリ以上であること**を要求する。

### 7.2 測定できる軸（開発側で判定する・必須）

| # | 軸 | 合否条件 | 手段 |
|---|---|---|---|
| B-1 | 記録の手数 | 1セットを記録するまでのタップ数が基準アプリ以下 | 手数を数える |
| B-2 | 情報密度 | ホームの初期表示DOMに次の5要素が全て存在すること: (1) 今日のプログラム名 (2) 今週の実施回数／目標回数 (3) 本日のタンパク質 実績／目標 (4) 本日のカロリー 実績／下限 (5) 最終トレ日からの経過日数。**5/5で合格、4以下で不合格** | V-3 |
| B-3 | 部位の可視化 | 直近7日に刺激した部位と未刺激部位が、スクロールなしで同時に判別できること。かつ刺激/未刺激が**色以外の属性**（テキストまたは `aria-*`）でも区別できること | V-3 |
| B-4 | 数値の信頼性 | 表示する全ての推定値に、推定であることの明示と誤差の説明が伴うこと（FFM推定・EAフロア・維持カロリー・トレンド） | DOM文字列の検査 |
| B-5 | オフライン | 機内モードで全6タブが描画され、セット記録が保存できること | V-3（`serviceWorker` 経由で offline を模擬） |
| B-6 | 初回起動 | データ0件の状態で全6タブが例外を投げずに描画され、ホームに次の行動を指示する文字列が1つ以上存在すること | V-3 |
| B-7 | 片手到達 | R4.2.2 と同じ（`#tabbar` と `.setbtn` の `getBoundingClientRect().top >= 812 × 2/3`） | V-3 |

### 7.3 測定できない軸（実機・所感の記録欄）

以下は**合否判定に使わない。** 判定基準を書けないものを「必須プロセス」にすると、その工程を誰も通過できなくなる。

- 配色の説得力、余白とタイポグラフィの質
- 汗ばんだ手での実際のタップ成功率
- カメラ、バイブレーション、Wake Lock の実挙動
- 電池消費
- 競合アプリとの並置による見た目の比較（**競合アプリの画面を取得する手段が開発環境に無い**）

> 以前の版は「実行できない検証手順を要求事項に書いても、満たされたか誰も判定できない」と正しく述べた直後に、`getBoundingClientRect` を「実行できない」側に分類し（誤り。実行できる）、ブラインド視覚比較を必須プロセスとして課していた（実行できない）。**この2つを取り違えると、実行できる検証が捨てられ、実行できない検証が門になる。**
>
> また「エージェントが優劣を明言しなかった場合は無効とし再実施」「『一長一短』は回答として認めない」という手順も削除する。**実態が同等であるとき、この手続きは判定者に虚偽の断定を強制する。** 手順が判定結果を作り出しており、検証として機能しない。同等と判定した場合は、その根拠となる測定値を両者について示させること。

### 8.2 検証環境

`scripts/dev-slow-server.mjs` は「応答が返らない回線」を再現するための開発用サーバー（テスト専用・本番には関与しない）。

```
node scripts/dev-slow-server.mjs 8081 0
curl "http://localhost:8081/__delay?ms=99999"   # 半死の回線にする
curl "http://localhost:8081/__delay?ms=0"       # 正常に戻す
```

**サーバーを止めるだけでは半死の回線を再現できない。** 接続拒否は即座に失敗するので、Service Worker の catch 節がすぐ走り、タイムアウトの経路を一度も通らない。R6.2.6 の8秒問題は、このサーバーを立てて初めて見えた。
